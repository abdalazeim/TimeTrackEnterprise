  QUICK START FOR FLUTTER
════════════════════════════════════════════════════════════════════════════════

  BASE = "https://goodstransportationsystem.onrender.com"

  1) Get a JWT token:
     POST {BASE}/api/v1/auth/token/
     Body: {"username": "...", "password": "..."}
     Response: {"success":true,"message":"تم تسجيل الدخول بنجاح",
                "data":{"access":"...","refresh":"...",
                        "user":{"id":..,"username":"..."},
                        "token_type":"Bearer"}}

  2) Use it in every request:
     Headers: {"Authorization": "Bearer <access>"}

  3) Refresh when expired:
     POST {BASE}/api/v1/auth/token/refresh/
     Body: {"refresh": "<refresh_token>"}

  4) Get user profile:
     GET {BASE}/api/v1/auth/me

  5) Sync data (pull/push):
     GET  {BASE}/api/v1/sync/?cursor=<last_cursor>&models=shipment,trip
     POST {BASE}/api/v1/sync/   Body: {"operations":[...]}

  Response envelope (standard success shape):
     {"success": true, "message": "...", "data": ..., "errors": null}

  Errors use the SINGULAR key:
     {"success": false, "error": "..."}

  Some list/detail endpoints return bare arrays or keyed objects;
  every such exception is listed in NOTES and beside its section.

      session security per route, Django <int:id> converters as OpenAPI
      path parameters. Regenerate the offline copy (docs/api/openapi.json)
      with:  manage.py api_openapi
    * The test suite pins all three together: resolver route set ==
      served spec == command output, so the spec cannot drift.

  NOTES
════════════════════════════════════════════════════════════════════════════════

  * All endpoints are available under BOTH /api/ and /api/v1/.
    Use /api/v1/ for Flutter — it is versioned and stable.

  * Response shapes — MEASURED (resolver AST + live web UI), 2026-10-15:
    - Standard envelope: {"success": true, "message": "...",
      "data": ..., "errors": null}                (api_response)
    - Paginated lists:   data = {"items": [...], "meta": {...}}
    - Every error:       {"success": false, "error": "..."}
      (SINGULAR key "error" — "errors" exists only inside the
      envelope above, where it is null unless the view fills it)
    - Create/edit actions: {"success": true, "message": "...",
      "<entity>": {...}}  (entity key at top level, no "data")
    - JWT obtain: data = {"access", "refresh", "user": {id,
      username}, "token_type": "Bearer"}; refresh rotates both
      tokens — store the new refresh or treat failure as logout.
    - Documented exceptions that are NOT envelopes — the web UI
      reads them by key; do not re-wrap them client-side:
        GET /users, /users/groups, /users/roles  -> bare JSON array
        GET /backup/list                         -> bare JSON array
        GET /users/permissions                   -> {permissions, groups}
        GET /settings/lookups                    -> {lookups: [...]}
        GET /settings/system, /settings/all      -> {settings: [...]}
        GET /settings/lookups/<id>               -> bare item object
        GET /dashboard/stats                     -> flat stats object
        GET /auth/status                         -> {logged_in, user}
      Section notes beside each table repeat the local shape.

  * Authentication: JWT Bearer token in Authorization header.
    Anonymous requests to protected endpoints return 401.

  * Update endpoints accept both PUT and PATCH (PATCH behaves as PUT;
    measured across every modules/*/items/<id>/update/ route).

  * Rate limits:
    - auth/token:  10 requests/minute (shared with auth/login)
    - sync:        300 requests/minute
    - other APIs:  60 requests/minute

  * The ledger endpoint requires account_id (integer PK), not account code.

  * Sync pull returns up to 500 rows per model per page.
    Use ?page=2 to get the next page.

  * CORS is enabled for cross-origin requests.

  * The production server is on Render free tier and may sleep.
    First request after idle takes ~30-60 seconds to wake up.
