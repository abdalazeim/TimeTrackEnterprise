# الوثيقة التقنية
## تطبيق Flutter لإدارة نقل البضائع — Offline-First Architecture

**المشروع:** Goods Transportation System  
**تطبيق الهاتف:** Flutter for Android  
**الخادم الخلفي:** Django REST API + Gunicorn  
**الاستضافة:** Render  
**قاعدة البيانات:** Neon PostgreSQL 16  
**المصادقة:** JWT Authentication  
**المزامنة:** Offline-First Synchronization

---

## 1. نظرة عامة على البنية المعمارية

يعتمد النظام على تطبيق Flutter يعمل على أجهزة Android، مع إمكانية استخدامه دون اتصال بالإنترنت، من خلال تخزين البيانات محليًا باستخدام SQLite، ثم مزامنتها مع خادم Django عند توفر الاتصال.

### 1.1 المخطط المعماري

```text
┌─────────────────────────────────────────────────────────┐
│                  Flutter Android App                    │
│                                                         │
│  ┌──────────┐ ┌────────────┐ ┌──────────┐ ┌───────────┐ │
│  │ SQLite   │↔│ Sync Engine│↔│ Auth JWT │↔│ API Client│ │
│  │ Offline  │ │ Pull /Push│ │ Token    │ │ HTTP      │ │
│  └──────────┘ └────────────┘ └──────────┘ └───────────┘ │
│                                                         │
│             Local State Management                      │
└──────────────────────────┬──────────────────────────────┘
                           │
                           │ HTTPS + JWT Bearer
                           ▼
                ┌──────────────────────┐
                │     Render (PaaS)    │
                │  Django REST API     │
                │  Gunicorn            │
                └──────────┬───────────┘
                           │
                           │ DATABASE_URL + SSL
                           ▼
                ┌──────────────────────┐
                │      Neon DBaaS      │
                │   PostgreSQL 16      │
                └──────────────────────┘
```

### 1.2 مسؤوليات المكونات

| المكوّن | المسؤولية |
|---|---|
| Flutter | واجهة المستخدم وإدارة عمليات التطبيق |
| SQLite | تخزين البيانات محليًا للعمل دون إنترنت |
| Sync Engine | إرسال العمليات واستقبال تحديثات الخادم |
| JWT Auth | تسجيل الدخول وإدارة رموز المصادقة |
| API Client | الاتصال بمسارات Django API |
| Django REST API | معالجة الطلبات والتحقق من الصلاحيات |
| Render | تشغيل التطبيق الخلفي واستضافته |
| Neon PostgreSQL | تخزين البيانات المركزية |

## 2. الاتصال بين Flutter وDjango API

يتواصل التطبيق مع الخادم عبر HTTPS، ويستخدم JWT للوصول إلى المسارات المحمية.

### 2.1 تسجيل الدخول

**الطلب:**

```http
POST /api/v1/auth/token/
Content-Type: application/json
```

```json
{
  "username": "driver1",
  "password": "***"
}
```

**الاستجابة المتوقعة وفق عقد API:**

```json
{
  "access": "eyJ...",
  "refresh": "eyJ..."
}
```

قد تختلف بنية الاستجابة الفعلية إذا كان الخادم يغلّف البيانات داخل `data`؛ لذلك يجب اعتماد التنسيق الذي يعيده المسار فعليًا.

### 2.2 جلب البيانات والتغييرات

```http
GET /api/v1/sync/?cursor=<last_cursor>
Authorization: Bearer <access_token>
```

تتضمن الاستجابة، بحسب عقد المزامنة، التغييرات الجديدة ومؤشر المزامنة التالي وسجلات الحذف عند دعمها.

### 2.3 إرسال العمليات المعلّقة

```http
POST /api/v1/sync/
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "operations": [
    {
      "operation_id": "UUID",
      "kind": "shipment.create",
      "payload": {}
    }
  ]
}
```

يعالج الخادم العمليات، ويعيد نتائجها وفق التنسيق المعتمد في API. يجب على التطبيق حفظ النتائج وتحديث حالة كل عملية محلية.

## 3. آلية المصادقة باستخدام JWT

### الخطوة الأولى: تسجيل الدخول

1. يُدخل المستخدم اسم المستخدم وكلمة المرور.
2. يرسل Flutter بيانات الاعتماد إلى `/api/v1/auth/token/`.
3. يتحقق Django من بيانات الاعتماد.
4. يستقبل التطبيق رمزي `access` و`refresh`.
5. يحفظ التطبيق الرموز بصورة آمنة.

### الخطوة الثانية: الوصول إلى المسارات المحمية

مثال:

```http
GET /api/v1/modules/transport/shipments/
Authorization: Bearer <access_token>
```

يتحقق الخادم من صحة الرمز وصلاحيته، ثم ينفذ الطلب بعد التحقق من صلاحيات المستخدم ونطاق البيانات المسموح له بالوصول إليها.

### الخطوة الثالثة: تجديد الرمز

```http
POST /api/v1/auth/token/refresh/
Content-Type: application/json
```

```json
{
  "refresh": "<refresh_token>"
}
```

إذا كان رمز التجديد صالحًا، يعيد الخادم رمز وصول جديدًا وفق إعداداته.

**متطلبات التنفيذ:**

- معالجة انتهاء صلاحية `access token`.
- منع تنفيذ طلبات تجديد متعددة بالتزامن دون داعٍ.
- إعادة محاولة الطلب الأصلي بعد نجاح التجديد.
- إنهاء الجلسة عند رفض رمز التجديد.
- عدم تخزين كلمات المرور أو الرموز داخل ملفات نصية مكشوفة.

## 4. آلية المزامنة Offline-First

تعتمد آلية العمل على إبقاء التطبيق قابلًا للاستخدام دون اتصال، مع إرسال العمليات إلى الخادم عند عودة الإنترنت.

### 4.1 أول تشغيل — المزامنة الكاملة

```text
Flutter
   │
   ├── GET /api/v1/sync/?models=shipment,trip
   │
   ▼
Django API
   │
   ├── جلب البيانات المسموح بها
   ├── إرجاع البيانات ومؤشر المزامنة
   │
   ▼
Flutter
   └── حفظ البيانات في SQLite
```

يجب أن يدعم الخادم جلب البيانات الأولية بطريقة متوافقة مع عقد المزامنة الفعلي.

### 4.2 العمل دون اتصال

عند إنشاء شحنة أو تعديل بيانات محلية:

1. يحفظ التطبيق التغيير مباشرة في SQLite.
2. يضيف العملية إلى جدول `pending_operations`.
3. يعرض التطبيق البيانات للمستخدم دون انتظار الخادم.
4. تبقى العملية معلّقة حتى تتوفر إمكانية المزامنة.

### 4.3 إرسال العمليات عند عودة الاتصال

```text
Flutter
   │
   ├── POST /api/v1/sync/
   │
   ▼
Django API
   │
   ├── التحقق من العملية والصلاحيات
   ├── منع تكرار التنفيذ
   ├── تنفيذ العملية وتسجيل نتيجتها
   │
   ▼
Flutter
   └── تحديث حالة العملية في SQLite
```

يجب ألا يعتبر التطبيق العملية ناجحة لمجرد إرسال الطلب؛ بل ينتظر نتيجة مؤكدة من الخادم.

### 4.4 المزامنة الدورية

```http
GET /api/v1/sync/?cursor=<last_cursor>
```

يستقبل التطبيق التغييرات منذ آخر مؤشر محفوظ، ثم يدمجها في SQLite ويحدّث مؤشر المزامنة بعد نجاح المعالجة المحلية.

يجب أن تتضمن الآلية معالجة تعارضات البيانات، وسجلات الحذف `Tombstones`، وإمكانية إعادة المحاولة عند فشل الاتصال.

## 5. تصميم قاعدة البيانات المحلية SQLite

تحتوي قاعدة البيانات المحلية على نسخ من البيانات اللازمة للتشغيل، إضافة إلى جدول العمليات المعلّقة وحالة المزامنة.

### 5.1 الجداول الأساسية

| الجدول | الغرض |
|---|---|
| `shipments` | بيانات الشحنات |
| `trips` | بيانات الرحلات |
| `customers` | بيانات العملاء |
| `pending_operations` | العمليات التي تنتظر المزامنة |
| `sync_state` | حالة المزامنة وآخر مؤشر مستلم |

يجب توسيع الجداول وفق النماذج الفعلية التي يحتاجها التطبيق، مع تحديد المفاتيح الأساسية والفهارس والقيود اللازمة.

### 5.2 جدول العمليات المعلّقة

```text
pending_operations
├── operation_id    UUID — معرّف فريد للعملية
├── kind            نوع العملية
├── payload         بيانات العملية بصيغة JSON
├── created_at      وقت الإنشاء
├── status          حالة العملية
└── retry_count     عدد محاولات الإرسال
```

الحالات المقترحة:

- `pending`: في انتظار الإرسال.
- `sent`: أُرسلت، ولكن لم تُحسم النتيجة محليًا.
- `applied`: أكد الخادم نجاح التنفيذ.
- `failed`: فشلت العملية وتحتاج إلى معالجة.

يفضل إضافة تفاصيل الخطأ ووقت آخر محاولة، مع التمييز بين الأخطاء المؤقتة والأخطاء النهائية.

### 5.3 جدول حالة المزامنة

```text
sync_state
├── last_cursor
├── last_sync_at
└── last_sync_status
```

يجب حفظ مؤشر المزامنة ومعالجة البيانات المرتبطة به بطريقة تضمن عدم فقد التغييرات إذا توقف التطبيق أثناء العملية.

### 5.4 اختيار مكتبة SQLite

يمكن استخدام إحدى المكتبتين:

- `Drift`: مناسبة للمشروعات المنظمة، وتوفر استعلامات مكتوبة ودعمًا للمعاملات.
- `sqflite`: مناسبة للتعامل المباشر مع SQLite، مع كتابة الاستعلامات وإدارة الترحيلات يدويًا.

**التوصية:** استخدام Drift إذا كان التطبيق سيحتوي على عدة وحدات مترابطة وعمليات مزامنة معقدة.

## 7. إعدادات بيئة الإنتاج على Render

مثال توضيحي لملف `render.yaml`:

```yaml
envVars:
  - key: SECRET_KEY
    sync: false

  - key: DATABASE_URL
    sync: false

  - key: DJANGO_SETTINGS_MODULE
    value: config.settings.production

  - key: ALLOWED_HOSTS
    value: goodstransportationsystem.onrender.com
```

**ملاحظات مهمة:**

1. يجب تعيين `SECRET_KEY` من إعدادات Render، وعدم تضمينه في مستودع GitHub.
2. يجب تعيين `DATABASE_URL` باستخدام سلسلة الاتصال الفعلية لقاعدة Neon.
3. يجب ضبط SSL لاتصال PostgreSQL وفق متطلبات مزود قاعدة البيانات.
4. يجب أن تتطابق قيمة `ALLOWED_HOSTS` مع اسم النطاق الفعلي.
5. يجب ضبط `CORS_ALLOWED_ORIGINS` عند الحاجة إلى السماح لواجهات ويب من نطاقات محددة؛ ولا يُعد CORS بديلًا عن المصادقة.
6. يجب التحقق من إعدادات الإنتاج الفعلية قبل اعتماد الملف، وعدم افتراض أن المثال يطابق إعدادات النشر الحالية.

## 8. الحالة الحالية للمكونات الخلفية

وفق المعلومات المقدمة عن المشروع، فإن الحالة المعلنة للمكونات هي:

| المكوّن | الحالة المعلنة | الملف أو المسار المرتبط |
|---|---|---|
| JWT Authentication | يعمل | `token_views.py`, `jwt_auth.py` |
| Sync Pull | يدعم 20 نموذجًا | `synchronization/views.py` |
| Sync Push | يدعم 3 عمليات | `synchronization/services.py` |
| Idempotency | مطبّق | جدول `sync_operation` |
| Tombstones | مدعوم | جدول `sync_tombstone` |
| Row Scoping | تمت معالجته | `transport_repository.py` |
| Rate Limiting | مفعّل | `rate_limit.py` |
| OpenAPI Schema | المسار محدد | `/api/v1/schema/` |

هذه الحالات منقولة من وصف المشروع، ولا تعني أنها خضعت لتحقق مستقل في هذه الوثيقة.

### اختبارات يجب إتمامها

- اختبار تسجيل الدخول ورموز JWT.
- اختبار صلاحيات المستخدم ونطاق البيانات.
- اختبار المزامنة الكاملة والتزايدية.
- اختبار إعادة إرسال العملية نفسها وعدم تكرار تنفيذها.
- اختبار الحذف والتعديلات المتزامنة.
- اختبار انقطاع الإنترنت أثناء الإرسال.
- اختبار استعادة التطبيق بعد الإغلاق المفاجئ.
- اختبار استجابات API الفعلية ومخطط OpenAPI.

## 9. المتطلبات الأمنية قبل الإطلاق

### 9.1 الضوابط المذكورة على الخادم

وفق وصف المشروع:

- JWT بصلاحية محدودة، مع مدة معلنة لرمز الوصول تبلغ 60 دقيقة.
- تحديد معدل الطلبات على المصادقة والمزامنة.
- تقييد CORS.
- حماية CSRF للعمليات المعتمدة على الجلسات.
- رفض تشغيل Django عند غياب `SECRET_KEY`.

ينبغي مراجعة الإعدادات الفعلية للتأكد من تطبيق هذه الضوابط، ومن أن قيم تحديد معدل الطلبات مناسبة للاستخدام الحقيقي.

### 9.2 التحسينات الأمنية المقترحة

1. **تدوير Refresh Tokens:** تفعيل التدوير وإبطال الرموز القديمة وفق سياسة الجلسات.
2. **التخزين الآمن:** استخدام مخزن آمن للرموز، مثل `flutter_secure_storage`، مع مراعاة حماية مفاتيح التشفير.
3. **تشفير البيانات المحلية:** تقييم SQLCipher إذا كانت حساسية بيانات النقل تستدعي تشفير قاعدة SQLite.
4. **التحقق من الصلاحيات:** عدم الاكتفاء بصحة JWT؛ يجب فحص صلاحية المستخدم لكل عملية.
5. **حماية سجلات المزامنة:** عدم تسجيل كلمات المرور أو الرموز أو البيانات الحساسة في السجلات.
6. **معالجة الأجهزة المفقودة:** توفير إمكانية إبطال جلسة الجهاز من جهة الخادم.
7. **التعامل مع الشبكة:** استخدام HTTPS فقط وعدم تعطيل التحقق من شهادة TLS.
8. **التعامل مع تعارض البيانات:** اعتماد سياسة واضحة لتعارض تعديلات المستخدمين.
9. **النسخ الاحتياطي:** التأكد من وجود آلية نسخ احتياطي واستعادة لقاعدة البيانات المركزية.

لا يُعد Device Fingerprinting وحده وسيلة موثوقة للمصادقة، ولا ينبغي استخدامه بديلًا عن إدارة الجلسات والصلاحيات.

## 10. تدفق البيانات الكامل

| المرحلة | تطبيق Flutter | الخادم وقاعدة البيانات |
|---|---|---|
| تسجيل الدخول | يرسل بيانات الاعتماد ويستقبل JWT | يتحقق من بيانات الاعتماد |
| فتح التطبيق | يقرأ آخر بيانات من SQLite | لا يلزم الاتصال لعرض البيانات المحلية |
| إنشاء شحنة دون إنترنت | يحفظ الشحنة ويضيف العملية إلى الطابور | لا يتلقى العملية في هذه المرحلة |
| عودة الاتصال | يرسل العمليات المعلّقة | يتحقق من العملية وينفذها |
| تأكيد التنفيذ | يحدّث حالة العملية المحلية | يعيد النتيجة المؤكدة |
| المزامنة الدورية | يطلب التغييرات منذ آخر مؤشر | يعيد التغييرات المسموح بها |
| دمج التغييرات | يحدّث SQLite ويحفظ المؤشر | يحتفظ بالبيانات المركزية |

### مثال توضيحي

```text
المستخدم
   │
   ▼
Flutter App
   │
   ├── قراءة البيانات المحلية
   │
   ├── إنشاء شحنة دون إنترنت
   │      └── SQLite + Pending Operation
   │
   ├── عودة الاتصال
   │      └── POST /api/v1/sync/
   │
   ▼
Django API
   │
   ├── التحقق من المصادقة والصلاحيات
   ├── منع تكرار التنفيذ
   └── حفظ العملية
          │
          ▼
     Neon PostgreSQL
          │
          ▼
     نتيجة التنفيذ
          │
          ▼
     Flutter + SQLite
```

## 12. الخلاصة

يهدف التصميم إلى بناء تطبيق Android باستخدام Flutter، مرتبط بنظام إدارة نقل البضائع الحالي عبر Django REST API، مع الاحتفاظ بقاعدة بيانات محلية تتيح الاستخدام دون إنترنت.

البنية المقترحة هي:

- **Flutter:** واجهة التطبيق ومنطق العمل المحلي.
- **SQLite:** تخزين البيانات وإدارة العمليات المعلّقة.
- **Django REST API:** المصادقة ومعالجة الطلبات والمزامنة.
- **Render:** استضافة الخادم الخلفي.
- **Neon PostgreSQL:** قاعدة البيانات المركزية.

وفق وصف المشروع، توجد بالفعل مكونات خلفية للمصادقة والمزامنة وتحديد معدل الطلبات. أما اكتمالها الفعلي وجاهزيتها للإنتاج، فيجب تأكيدهما بالاختبارات ومراجعة الكود والاستجابات الحقيقية.

**الهدف النهائي:** بناء تطبيق Flutter متكامل يعمل على Android، ويدعم الاستخدام دون اتصال، ويحافظ على اتساق البيانات مع النظام الحالي عند عودة الاتصال بالإنترنت.
